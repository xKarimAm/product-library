Center of Claude

Where did I leave off?

Thirty-odd projects, each with its own Claude Code history. COC turns all of it into a small city you can read from across the room: what is live, what is stuck, and what is waiting on you.

This deck is the story of how it was built and everything it taught us. Use the arrow keys, or the skyline at the bottom.

Open poc_city.html from the repository root to see the city running.

The real thing, live: the city POC running on made-up demo projects.

Chapter 1

The answer already existed. Nobody was reading it.

Answering "where did I leave off?" meant opening each project folder by hand. Yet Claude Code already writes a registry of every project, and each project keeps a session-state file that says exactly where to pick up. COC builds nothing new. It reads what is already on disk.

What it reads

  • Claude Code's own registry: transcripts under ~/.claude/projects
  • Each project's .claude/session-state.md: the "pick up here" line and its blockers
  • Git branch, handoff notes, transcript sizes
>

What it is

  • coc.py, a stdlib Python server on 127.0.0.1:7777
  • index.html, one page of vanilla JS and SVG
  • Read-only over every project folder. It writes nothing.
>

The three jobs

  • Morning triage: what needs me first
  • Ambient board: a second screen that stays honest all day
  • Launcher: open a project in VS Code, or copy its resume command

The owner explicitly did not pick "something to show people". Every visual had to earn its place against those three jobs, and that rule decided most of what follows.

Chapter 2

Why another builder would run this

Zero install

Python's standard library and one HTML file. No pip, no npm, no build step. py coc.py and open the browser.

Nothing to maintain

It keeps no database and no state of its own. Delete it and nothing is lost; every fact comes from files Claude Code and your projects already write.

Decisions come to you

Start a blocker in a project's session-state with your name, like Me [M]: pick a vendor, and it becomes the headline count and a messenger walking to the front of the city. The name is set in one regex in waiting_on_me(); change it to yours.

Safe on a work machine

Loopback only, a Host allow-list, a per-run token on every API call, a nonce-based Content-Security-Policy, and launches that never go through a shell.

Readable at a glance

Height, colour, light and motion each carry one fact, so the state of every project reads without clicking anything.

Tested like it matters

Mutation tests, raw-socket HTTP checks, and browser probes that plant their own defects to prove they can fail. The lessons in this deck are why.

Chapter 8

Run it on your own projects

  1. Start the dashboard

    Windows with Python 3 and its py launcher. No install step. Other platforms are untested, and the probes expect Chrome at its Windows path.

    py coc.py

    Then open http://127.0.0.1:7777. The server lives as long as the terminal does.

  2. Give it something to read

    Keep a .claude/session-state.md in each project with a next_action line. Put decisions that need you in blockers, starting with your name. COC matches the name in waiting_on_me() in coc.py; it ships set to the author's, so change that regex first.

  3. Check it is healthy

    py coc.py --selftest

  4. Build the city from your own data

    Save your server's /api/projects response as tools/poc_data.json (git-ignored, never commit it). The API answers only with the X-COC-Token header; the token is printed in the page the server serves. Then build and probe:

    py tools/build_poc.py
    py tools/pocprobe.py

    The probe needs Google Chrome. It drives a headless copy over the DevTools protocol.
